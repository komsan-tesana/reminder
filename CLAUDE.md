# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static, browser-only React app (Vite + TypeScript) that imports Thai ERP transport-planning Excel files and shows them on a calendar (FullCalendar), with in-app editing, export, reminders and an installable PWA shell. There is no backend for the data: the app is hosted on GitHub Pages and all shipment data stays in the user's browser. The only server-side piece is an optional push relay (`worker/`, a Cloudflare Worker) that wakes phones at given times; it never sees shipment data. UI text is Thai; dates must support both Buddhist (พ.ศ.) and Gregorian (ค.ศ.) years.

## Commands

```bash
npm run dev            # Vite dev server (.claude/launch.json uses port 5173)
npm test               # vitest run (all tests)
npx vitest run src/lib/features.test.ts          # one file
npx vitest run -t "round-trips through the importer"   # one test by name
npx tsc -b             # typecheck (build runs this first)
npm run build          # tsc -b && vite build -> docs/  (NOT dist/)
npm run deploy         # release; see below
npm run deploy:minor / deploy:major
npx tsc -p worker      # typecheck the push relay (its tests already run in `npm test`)
npm run deploy:worker  # deploy the push relay to Cloudflare (separate from the app); -- --dry-run, -- --write-config
```

No linter is configured. To check a build without touching tracked files, pass `--outDir` to `npx vite build` (the default output dir `docs/` is committed). Tests are plain-node vitest (no DOM): keep logic that needs testing in pure `src/lib` modules, and `await import()` inside tests for modules that touch browser globals.

## Release / deploy flow (important)

- Work happens on `develop`. `scripts/deploy.sh` **must be run from `develop`** and refuses otherwise, or with uncommitted changes, or if `develop` is behind/diverged from `origin/develop` (being ahead is fine; it pushes).
- The script: `npm ci` → `npm test` → bump version (`npm version`, patch by default) → build → commit `chore: release vX.Y.Z` + tag → merge `develop` into `main` (`--no-ff`) → push `develop`, `main`, tag → return to `develop`.
- GitHub Pages serves **`main` branch, `/docs` folder** ("Deploy from a branch"; there is no Actions workflow). So `docs/` is committed build output: never edit it by hand, and don't commit a build made outside the deploy script.
- Version and build date are injected at build time from `package.json` via `define` in `vite.config.ts` (`__APP_VERSION__`, `__BUILD_DATE__`, declared in `src/env.d.ts`) and shown in the top bar.
- `vite.config.ts` sets `base: './'` so the build works under the GitHub Pages sub-path.

## Architecture

Data flow: **xlsx/csv → worker parse → column mapping → `Shipment[]` → IndexedDB → filters → grouping → calendar / detail panel**. `App.tsx` owns all state (shipments, reminders, settings, filters, selection, panel size) and passes it down; rarely used dialogs (import, data, reminders, edit, settings) are `React.lazy`-loaded, and `xlsx` is dynamically imported for export to keep the main bundle small.

### Data and import
- `src/types.ts`: `Shipment` is one spreadsheet row (not one calendar event). `FIELDS` defines the mappable columns and the header regexes used by auto-mapping. Dates are always stored as Gregorian ISO `yyyy-mm-dd`; era only matters on parse and display.
- Import (`readWorkbook.ts` → `parse.worker.ts` → `mapping.ts` → `dateParse.ts`): SheetJS runs in a Web Worker (files are ~4k rows). CSVs are decoded manually as UTF-8 (fallback Windows-874) because SheetJS would read them as Latin-1 and garble Thai. `autoMap` guesses columns from header names (saved per header-signature in localStorage); `buildShipments` produces items + row errors. The effective date is `confirmedDate ?? requestedDate`. Row ids are a hash of date|SO|item|description|qty plus an occurrence counter, so re-importing the same file is idempotent.
- `dateParse.ts` handles Excel serial numbers, `dd/mm/yyyy` (day first) and ISO text, and Buddhist years (auto-detected when year > 2400, or forced). Years outside 1900–2200 are rejected, so choosing the wrong era surfaces as import errors rather than bad dates.
- Storage (`db.ts`): shipments and reminders live in IndexedDB via Dexie (4k rows exceed the localStorage quota). localStorage holds only small things: `Settings` (era, groupBy, theme, notify, display), saved column mappings, panel size, last-digest date. Dexie schema is versioned (`version(2)` added reminders): add a new `version(n)` rather than editing old ones. `loadSettings` merges saved values over defaults and migrates old shapes (e.g. `notify.tomorrow` → `daysAhead`); do the same when changing `Settings`.
- Edited rows: `editShipments` sets `editedAt` and, when the date moves, `confirmedDate`. `commitImport` in merge mode skips rows whose existing copy has `editedAt`, so ERP re-imports never overwrite local edits (ids stay stable because they derive from the original date). Replace mode and backup restore are the only ways to overwrite them.

### Display
- Calendar (`group.ts`, `CalendarView.tsx`): rows are grouped per day by customer / SO / truck into one chip each (a day can have ~90 rows). Customer chips use `shortName` (drops บริษัท/จำกัด etc.), full name in the tooltip. FullCalendar's Thai locale would force Buddhist years, so titles use a custom `titleFormat` driven by the era setting. FullCalendar sits in a `.fc-host` wrapper with a `ResizeObserver` calling `updateSize()` so it follows panel-resize drags (`CalendarApi` has no `el`).
- Hidden columns (`available.ts`): a field with no data in any row (not mapped on import, or empty everywhere) disappears from the detail table, the filters, the group-by options and the colour tones that depend on it; it reappears as soon as any row has data. The edit dialog intentionally still offers every field so a plan can be filled in from scratch.
- Status colours (`tones.ts`, `SettingsModal.tsx`): chip colour comes from the group's tone (assigned / pending when status contains "ค้าง" / unassigned). Users can switch tones off or recolour them; hidden tones render as a neutral `tone-none` chip. Defaults must keep ≥ 4.5:1 contrast with the white chip text (tested); `migrateToneColor` upgrades saved colours that still equal an old default (settings are saved whole, so old defaults stick otherwise). Colours reach CSS as `--assigned/--pending/--unassigned` inline on `.app`.
- Theme (`theme.ts`): `system | light | dark`. `main.tsx` applies it to `<html data-theme>` before first render (no flash); `system` removes the attribute so the stylesheet's `prefers-color-scheme` rule applies. The dark palette is written twice in `styles.css` (pinned and OS-driven) and must be edited in both places. Use `--accent-fill` (not `--accent`) for backgrounds carrying white text and `--warn` for warning text so both themes stay readable.
- Detail panel layout: `ResizeHandle.tsx` is a splitter between calendar and panel (width on desktop, height when stacked below 820px). Size is stored as px and applied through `--panel-w` / `--panel-h` on `<main>`, capped in CSS with the same constants (`EDGE_W`, `MAX_VH`) the drag clamp uses, so a saved size cannot swallow a smaller window. Stacked mode scrolls the page, so its ceiling is viewport-based, not `<main>`-height-based.
- UI kit: Tailwind CSS v4 (`@tailwindcss/vite`) plus Radix UI (`react-dialog`, `react-popover`). `styles.css` imports only Tailwind's theme tokens and utilities, **not preflight**, so the hand-written CSS still works; its colour variables are exposed as `bg-card`, `text-ink`, `border-line`, `text-accent`… via `@theme inline`. The old rules are *unlayered* and beat utility classes on the same property, so remove an element's old rule before restyling it with utilities (this is why `.ss input` still lives in CSS). Migrated so far: `Modal` (Radix Dialog, also used by `ImportWizard`), `SearchSelect` list (Radix Popover anchored to the input, focus stays in the input), `Select` (Radix Select, replaces every native `<select>`; "" option values travel as a placeholder), `Checkbox` (Radix Checkbox, a button with role=checkbox, so it needs `!` utilities against the unlayered `button` rules), `DatePicker` (date-only variant used by the edit dialog), `ColumnFilter` (header filters in the detail table) with the detail and reminder tables driven by TanStack Table v8 (`@tanstack/react-table@8`: v9 is the npm `latest` but has a different API; column hints `th`/`td`/`filter` live in `ColumnMeta`, see `src/tanstack.d.ts`; don't pass `cell: undefined` in a column def, it overrides the default renderer) and `DateTimePicker` (react-day-picker + hour/minute columns); notices are `sonner` toasts (top-right, auto-close 8 s; `App.tsx` `push()` wraps `toast()`, colours come from `[data-sonner-toaster]` rules in `styles.css`); everything else is still plain CSS, move it over gradually.
- Font: IBM Plex Sans Thai, bundled via `@fontsource` (weights 400/600/700, `latin` and `thai` subsets only, imported in `main.tsx`; no request to Google Fonts, works offline in the PWA). System fonts stay in the `font-family` fallback list. Tables and the calendar use tabular digits.
- **Working on Buddy? Use the project skill `.claude/skills/buddy/`** (map of the code, checklists for adding items / animations / stats / special days, how to verify) instead of re-reading these files; the bullet below is the summary.
- Buddy "เปี๊ยก" (`Buddy.tsx`, `lib/buddy.ts`, `lib/buddySprite.ts`): a pixel cat fixed to the bottom edge. Original art built in code (poses painted from rectangles onto a grid, 1px outline traced automatically, rendered as merged SVG paths; no image files, and not copied from any meme sprite). `buddy.ts` is pure and tested: time-of-day periods, weighted next-activity choice (sit/walk/yawn/sleep/play/happy; livelier in the morning, drowsy after lunch, asleep at night), durations, Thai jokes per period, work-aware jokes from `WorkCtx` (computed in `App.tsx` from local data, never sent anywhere), click replies and poke milestones. `Buddy.tsx` only drives it: one timeout chain (paused while the tab is hidden), two-frame animation ticker only while walking/playing, a rare idle bubble (90–200 s, never over a dialog), `prefers-reduced-motion` keeps it sitting/sleeping. Settings: `settings.buddy {visible, sound, skin, outfit, toy}` (default shown, silent, calico, no outfit, no toy; `loadSettings` fills it for old saves) are edited in the cat's own dialog (`BuddyModal`, opened by the paw button `PawIcon` in the top bar, which shows a dot while earned items are unseen), no longer in the settings dialog; the bubble's ✕ also hides it. Progress lives in `localStorage` `reminder.buddy.v1` (`BuddyStats`: counted pokes, today's poke quota, visit days + total days + best streak, reminders ticked off, imports, night visits, perfect days, wakes, data counters (new rows imported, highest customers / SO / rows-in-a-day / months seen, exports, backup days, rows assigned and edited, filter uses), festivals seen, `earned` and `seen` item ids; `loadBuddyStats` validates every field). Pokes only count `DAILY_POKE_CAP` (200) a day, and a scared flurry does not count, so the thousand-poke unlocks take days. `earned` is permanent: `bump()` runs `withEarned`, so raising a threshold later never takes an item away, and a record saved before `earned` existed is run through `grandfather()` with the old poke thresholds (`LEGACY_POKES`) so nobody loses what they had. `buddyUnlocks.ts` (pure, tested) defines the unlock catalogue (`ITEMS`: fur colours, outfits, moves) with progress functions, streaks and `newlyUnlocked`; `App.tsx` `bump()` applies a stat change, saves it and toasts anything just unlocked. Wardrobe dialog = `BuddyModal.tsx` (from the settings dialog); the equipped skin/outfit are in `settings.buddy` and `safeLook` falls back to the default if they are not unlocked. Outfits are painted per layout (`Kind`: front/side/loaf/stretch/roll/stand) in `OUTFITS` before the outline is traced, so a new pose needs a layout kind and an entry for every outfit (the test checks every pose × outfit combination changes the sprite and fits the grid). The standing cat shares the sitting cat's head (`drawHead`), so head gear falls back to the `front` entry and only body pieces (scarf, vest, tie, medal, shirt) have their own `stand` coordinates; the zoomies reuse the `side` layout with different legs. Halloween (31 Oct) and Christmas (24–25 Dec) outfits, unlike the other festivals, need a poke on the day (`recordPet`), not just opening the app. Skins are palette overrides. Mouth toys are a separate slot (`TOYS` in `buddySprite.ts`, painted after the outfit); the data-driven toys (`buddyData.ts` computes the facts, numbers only) are small ASCII pictures in `TOY_ICONS` that `toyAnchor` places per layout (an id without a picture is unlocked and counted but `isShown`/`hasToyArt` keep it from being announced or worn). Unlocked moves (stretch, roll, tail-chase, face-washing, night zoomies, standing on two legs) are only chosen by `nextState` when passed in `allowed`; poking five times in three seconds triggers the `shout` easter egg. Festivals (`seasonOf`: Songkran 13–15 Apr, New Year 30 Dec–2 Jan, all of November for Loy Krathong) add outfit unlocks and jokes. `playMeow` in `sound.ts` is the synthesised meow. It is not rendered while the phone bottom sheet is open. Wrapper is `pointer-events: none`, only the cat and bubble take clicks.
- Phone layout (≤ 820px, the `stacked` flag in `App.tsx`): no side panel and no `ResizeHandle`. The calendar goes `compact` (no chips; each day shows a count badge in its most urgent tone via `dayCellContent`, tapping opens the whole day) and the day opens in `BottomSheet.tsx` (vaul, non-modal so the calendar stays tappable; snap points peek / half / full; the list only scrolls at full). `DetailPanel` has a `compact` mode: rows as tap-to-select cards, with the action bar *above* the list because the sheet is translated down at peek and anything at its bottom would be off-screen. The sheet owns a history entry (`App.tsx` `sheetOpen` effect) so Back / swipe-back closes it instead of leaving the app. `viewport-fit=cover` plus `env(safe-area-inset-bottom)` and `dvh` handle the iPhone home bar and Safari toolbar. FullCalendar's `dateClick` ignores synthetic `element.click()`; use real pointer clicks when testing.
- `FilterBar.tsx` uses `SearchSelect` (type-to-search combobox); on narrow screens the dropdowns fold behind a toggle. With no data, `App.tsx` shows an empty state that can load `sample.ts` demo rows.

### Export, reminders, PWA
- Export (`exporters.ts`): xlsx/CSV reuse the original ERP header names so exports re-import via `autoMap`; ICS (from the data dialog) emits one all-day event per group with stable UIDs, a growing `SEQUENCE` (re-importing updates events instead of duplicating them) and alarms at 09:00 the day before and 08:00 the day; JSON backup is validated field-by-field in `parseBackup` (unknown fields dropped).
- Reminders (`reminders.ts`, `useReminderEngine.ts`, `sound.ts`): pure date/digest logic is separate from the 30-second `setInterval` engine, which only runs while the tab is open (on iPhone that effectively means only while the app is on screen). `digestToFire` decides when, and the day is recorded as done only when a digest was actually produced, so work added later the same day is still announced. `dailyDigest` summarises today plus `daysAhead` days, one line per day (the on-open banner uses the same setting). One chime per tick (Web Audio, armed on first user gesture), only for digests and reminders, never for ordinary toasts.
- PWA (`public/manifest.webmanifest`, `public/sw.js`, registered in `main.tsx` for production builds only so dev is never cached): installable, works offline (network-first cache). iOS only delivers web notifications to an app added to the Home Screen; `platform.ts` detects that and the reminders dialog explains it. Notifications use `registration.showNotification` when a service worker is active (required on Android Chrome / iOS PWA), else `new Notification`. Bump `CACHE` in `sw.js` only if cache layout changes.
- Locked-screen alerts: the page cannot run timers once iOS suspends it, so locked-screen notifications come from Web Push (see the relay section below), driven by the daily-summary switch. A "sync to the phone's calendar" button existed (share sheet, `data:` link and a service-worker-served virtual `calendar.ics` were all tried on a real iPhone) and was removed on request; the plain `.ics` export in the data dialog is what remains. Browsers cannot write to a calendar directly, so if this ever returns, expect the OS to ask for confirmation and note that the Web Share sheet has no Calendar target for .ics and `data:`/blob: links do not open the Add-to-Calendar sheet.

### Web Push relay (`worker/`, optional)
Locked-screen notifications need a server, so `worker/` is a Cloudflare Worker + KV + per-minute cron, deployed with `npm run deploy:worker` (`scripts/deploy-worker.sh`; see `worker/README.md`). `scripts/deploy.sh` and GitHub Pages never touch it, so the two can drift: deploy.sh only prints a notice when `pushConfig.ts` is empty or `worker/` changed since the last release tag. The Worker is deployed first, then the app, because the app needs its URL and public key (`GET /health` returns `publicKey` derived from the deployed secret, and `deploy-worker.sh --write-config` copies URL + key into `pushConfig.ts`; a mismatched key makes every push fail). Privacy is the design constraint: the server stores only the device's push endpoint/keys and a list of epoch seconds to wake it. Notification *text* never leaves the device.
- Client (`pushPlan.ts`, `push.ts`, `outbox.ts`): `buildPushPlan` (pure) turns shipments + reminders + notify settings into `{schedule, outbox}`. `syncPush` writes the outbox (texts) to the separate IndexedDB `reminder-push`, then uploads only `schedule` to `POST /sync`. `App.tsx` re-syncs 3 s after any change and when the page becomes visible. There is no separate Push control: push is *wanted* while the daily summary is on OR at least one reminder is still pending (`pushWanted` / `countPendingReminders`), and `pushAction(state, wanted)` decides subscribe / unsubscribe / nothing (all pure, in `pushStatus.ts`, tested). `App.tsx` acts on it at the click that matters: switching the summary on (`toggleDigest`) or adding a reminder (`addReminder` starts the permission request before awaiting anything, because iOS only prompts inside a gesture) subscribes and syncs; switching the summary off, finishing or deleting a reminder lets go only when nothing else needs push (`releasePushIfIdle`), clearing the on-device outbox. Someone who already needed push before this install had a subscription is subscribed quietly at start-up, only if notification permission is already granted (never prompt without a click). Without a configured Worker (`src/lib/pushConfig.ts` empty) or where push is unavailable, the summary still works in-app and `describeDelivery` says so.
- Two dialogs share the Push status: `NotifyModal` (daily summary, opened by 🔔 การแจ้งเตือน) and `ReminderModal` (per-item reminders, opened by ⏰ เตือนรายการ and by the detail panel's "ตั้งเตือน"); `DeliveryNote` renders the shared status block in both.
- `public/sw.js` `push` handler: takes the due items from the outbox and shows them; if there are none it still shows a generic notice, because iOS revokes subscriptions whose pushes show nothing. Its DB name/store must match `outbox.ts`.
- Worker secrets: `VAPID_PRIVATE_JWK` and `VAPID_SUBJECT` (the owner's contact address) are Wrangler *secrets*, never `[vars]` in `wrangler.toml`, because the repo is public; `wrangler.toml` holds only non-secret config (allowed origins, KV id, cron). `configProblem` (in `app.ts`) checks them on every request/cron run so a missing or placeholder value yields a clear error (`/health` returns `{ok:false,error}`) instead of an opaque push-service rejection. Local dev reads them from the git-ignored `worker/.dev.vars`.
- Worker (`app.ts`, `store.ts`, `webpush.ts`): `/sync` validates (push-service hostname allowlist, key lengths, schedule capped at 300 and 120 days), replaces the device's schedule; cron wakes each device once per minute at most, drops wake-ups > 6 h stale, deletes devices on 404/410. Payload is encrypted per RFC 8291 (tested against the RFC's own vector and an independent library) and signed with VAPID. KV free-plan limits (1,000 writes and 1,000 list calls a day) shape `store.ts`: one `sub:<id>` record per device plus a shared `index` key of earliest wake-ups, so an idle cron minute is one read and no writes, an unchanged re-sync writes nothing, and nothing ever calls `list()`; abandoned devices expire via `expirationTtl`. The index is the only shared key (no locking in KV), so every `/sync` re-checks and repairs the device's entry, and `setSchedule` keeps a schedule synced while its push was in flight. ≤ 20 devices per cron run.
- Tests: `worker/*.test.ts` run in the root `npm test`; an in-memory `FakeKV` that counts reads/writes stands in for KV, `fake-indexeddb` lets `src/lib/sw.test.ts` run the real `public/sw.js`.

## Gotchas

- `xlsx` is installed from `https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz`, deliberately: the npm registry copy (0.18.5) has known vulnerabilities. Don't "fix" it back to a registry version.
- `@fullcalendar/*` packages must stay on the same major (6.x); `@fullcalendar/react` 7 doesn't match core 6.
- The source ERP file uses a non-standard `x:` XML namespace; SheetJS reads it fine, but hand-rolled XML parsing needs the prefix.
- Don't commit user data files (e.g. the sample ERP `.xlsx` from Downloads); use synthetic data (`sample.ts`, or a CSV built in the page) for tests and browser checks.
- Verifying the service worker needs a production build: `npx vite build --outDir <scratch>` then `vite preview --outDir <scratch>` (add a temporary entry to `.claude/launch.json` and revert it). The dev server never registers the worker.
- In the in-app browser pane, `resize_window` colour-scheme emulation is re-synced to the app theme whenever the theme changes, so a "system" theme can look wrong right after a toggle; set the emulation again before judging it.
